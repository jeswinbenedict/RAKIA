# Known Limitations

RAKIA is research software. These limitations are deliberate, documented, and shown in the product where relevant.

## Scientific

- **Not clinically validated.** Anomaly, trend and onset detection are evaluated only on synthetic scenarios with known ground truth. Those results are engineering metrics, not clinical sensitivity or specificity.
- **No real astronaut data.** Individual in-flight astronaut data is not publicly available at the needed granularity. Demonstrations use clearly labelled simulated data.
- **Indirect domains.** Bone density, immune status and neuro-ocular changes (SANS) cannot be measured by wearables. RAKIA shows them only as imported clinical or lab records plus mission context, and never infers them from vital signs.
- **The simulation mission is not a physiological model.** Its daily values come from simple statistical models with deliberately injected changes (a step, a gradual drift, a sensor outage). It exists to demonstrate and test the analytics, which run exactly as they would on real data. Its values say nothing about real astronauts.
- **Gradual changes may not raise an alert.** In the simulation, a decline of one baseline standard deviation over 30 days does not trigger the sustained-shift detector; it shows up only as a significant Theil-Sen trend. This is by design (the detector is tuned for a low false-alarm rate), and the UI reports the trend rather than a stronger signal.
- **Check-ins and the reaction-time test are self-measurement aids, not assessments.** The sleepiness and stress questions use published instruments (the Karolinska Sleepiness Scale; a validated single-item stress measure); the mood question is a simple self-rating and is labelled as not validated. RAKIA shows the answers as given and does not score, interpret or alert on them. The reaction-time task follows the 3-minute PVT-B protocol (1 to 4 s intervals, 355 ms lapse threshold, 100 ms false-start threshold), but touch and display latency differ between devices, so a result compares only with earlier tests on the same device; it has not been validated against a reference PVT device. These records stay on the device: sharing them with a flight surgeon (with consent scopes) is not built yet.
- **Small-sample science.** Much spaceflight evidence comes from small cohorts. Any population-derived "expected adaptation" reference is approximate and labelled as such.

## Technical

- **Sign-in is email and password only, and backup is upload only.** The app signs in with Firebase Authentication's REST API and creates the RAKIA account behind Turnstile. Turning on backup sends the astronaut's readings to the server; restoring them to another device, and showing medical staff a crew member's data, are not built yet. Backup needs lasting storage on the device, so a browser that cannot keep data offers none. Google sign-in needs Firebase's SDK or an OAuth redirect flow and is not offered; Phone sign-in needs Firebase's paid plan.
- **Turnstile protects RAKIA accounts, not Firebase sign-up itself.** The API creates an account only after verifying a Turnstile token with Cloudflare, so bots cannot fill RAKIA's database. Creating the Firebase sign-in (the step before) is protected by Firebase's own abuse limits: gating it with Turnstile would need a Firebase blocking function, which requires the paid Blaze plan.
- **Accounts are created in the web app.** Turnstile runs in a browser, so the native apps sign in to existing accounts but send people to the web app to create one.
- **Signing out does not revoke the session on Firebase's side.** The app forgets its refresh token; revoking tokens server-side needs the Firebase Admin SDK and a service account, which RAKIA deliberately does not hold.
- **Rate limits are per API instance.** Each instance keeps its own in-memory counters, so N instances allow up to N times the configured rate. Render's front end and Cloudflare in front of the web app add coarser protection. A shared limiter is needed only if abuse appears.
- **The API does not terminate TLS itself.** It is meant to run behind a TLS-terminating front end (Render, Cloud Run, or a local reverse proxy); it sends HSTS outside development and requires TLS (`verify-full`) to the database.

- **The server database checks the hash chain's links, not the hashes.** PostgreSQL enforces that each client's records continue the sequence and that every `prev_hash` equals the previous record's `hash`. Recomputing each record's SHA-256 from its fields is the API's job (with librakia, as on the device), which is not built yet.
- **Only part of the database design exists yet.** Migration `0001_core` holds identities, missions and membership, measurements, alerts, sync batches, the audit log and Turnstile replay protection. Mission phases, context events, self-assessments and consent, baselines, habitat and radiation records, evidence references and de-identified research views arrive with the features that use them.

- **Encryption at rest covers the native apps only.** On Android, iOS, Windows, macOS and Linux the database file is encrypted (ChaCha20-Poly1305, SQLite3 Multiple Ciphers) with a 256-bit key kept in the system keystore. In a browser there is no protected place to keep a key, so RAKIA does not encrypt browser storage; the Data management page says so. Encryption protects the file at rest (a copied file, a lost disk); it does not protect against malware running as the user on an unlocked device, which can ask the keystore for the key as RAKIA does.
- **A lost key means the local data cannot be read.** If the keystore entry disappears (keystore reset, operating-system reinstall, a file copied to another device), RAKIA leaves the encrypted file untouched, never replaces the key, and runs in memory with the reason shown. There is no in-app reset or recovery yet. Cloud backup and device-to-device transfer of the app's data are turned off on Android; on iOS the key is never restored to another device, so a database restored from a backup cannot be read there.
- **Browser storage depends on the browser.** The web store uses SQLite WebAssembly on the Origin Private File System where available, otherwise IndexedDB. If neither is available (some private-browsing modes), RAKIA keeps data in memory only and says so. Browser storage can be cleared by the user or evicted by the browser.
- **One hash chain per mission on the device.** Each mission's measurements form their own chain, so deleting a simulation mission never breaks the chain of a real one. The sync protocol (planned) will key server-side uniqueness on client, mission and sequence number.
- **Simulated readings are dated relative to the day the simulation starts**, so the latest simulated mission day is today. The values themselves are deterministic for a given seed; timestamps and record identifiers are not.
- **iOS** builds are verified only in CI on macOS runners (unsigned); the primary development machine is Windows.
- **Dart bindings:** `rakia_chain_verify` and `rakia_record_encode` are not exposed to Dart yet; the app verifies a stored chain by recomputing each record hash with `rakia_flat_record_hash` and checking the links. Ledger timestamps and sequence numbers passed from Dart must lie within ±(2^53 − 1) to stay exact on the web.
- **Web analytics core:** the web build depends on a WebAssembly module that must be compiled with Emscripten. If the module is missing or fails to load, the app says so on the About page and runs no analytics.
- **Local PostgreSQL is not Supabase.** Supabase-specific services (PostgREST, Realtime, Storage) are not available in local development unless the optional Docker-based Supabase stack is running.
- **No phone (SMS) sign-in.** Firebase sends SMS only on its paid Blaze plan; the zero-cost deployment offers email/password and Google sign-in.
- **Free hosting limits.** The API on Render's free plan sleeps after 15 minutes without requests, and the next request waits about a minute. Supabase's free plan pauses a project after 7 days without activity (restored from the dashboard), keeps 500 MB, has no automatic backups, and allows 2 active projects per account. Details: [DEPLOYMENT.md](DEPLOYMENT.md#zero-cost-hosting).
